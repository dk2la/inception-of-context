# Inception-of-Context (IoC) — разбор задания и план работ

> Документ для человека, который **не погружён в машинное обучение**.
> Хорошая новость: обучать модели здесь не нужно. Это проект по **инженерии и
> системному администрированию**: готовые модели скачиваются и соединяются
> между собой обычным кодом (Python, HTTP, файлы, Docker).

---

## 0. Суть проекта в одном абзаце

Нужно написать **свой маленький локальный аналог Copilot / Cursor**. Система:

1. **читает** небольшой проект с кодом и строит по нему «поисковый индекс по смыслу» (Part 1);
2. **отвечает на вопросы** об этом коде, подсовывая маленькой локальной языковой модели нужные куски кода (Part 2);
3. **сама правит код** по текстовой просьбе («добавь функцию…»), проверяет, что проект не сломался, а если сломался — пробует ещё раз (до 3 раз) и потом **откатывает всё назад байт-в-байт** (Part 3).

Всё работает **только локально**. Любой вызов облачной LLM (OpenAI, Claude, Gemini и т.п.) = **оценка 0**.

## 1. Словарик: минимум ML, который нужно понимать

| Термин | Что это простыми словами | Где в проекте |
|---|---|---|
| **LLM** (языковая модель) | Программа, которая по входному тексту продолжает текст. Для нас — «чёрный ящик»: отправил текст по HTTP → получил текст. | Part 2, 3 |
| **Ollama** | Программа-сервер, которая скачивает и запускает LLM у тебя на машине. Даёт HTTP API на `localhost:11434`. | везде |
| **3B** | 3 миллиарда параметров — размер модели. Чем меньше, тем быстрее и глупее. Лимит задания — ≤3B. | — |
| **qwen2.5:3b** | Instruct-модель: «болтает», отвечает на вопросы. | `/ask` (Part 2) |
| **qwen2.5-coder:3b** | Coder-модель: лучше пишет код и JSON. | патчи (Part 3) |
| **Токен / контекст** | Модель читает текст кусочками-токенами (~¾ слова). У маленькой модели «окно» — несколько тысяч токенов. **Весь проект в него не влезет** — поэтому и нужен поиск нужных кусков. | — |
| **Эмбеддинг (embedding)** | Превращение текста в список чисел (вектор, у `all-MiniLM-L6-v2` — 384 числа) так, что **похожие по смыслу тексты дают близкие векторы**. Делается одной строкой кода через библиотеку. | Part 1 |
| **Векторная БД** | База, которая хранит векторы + исходный текст + метаданные и умеет быстро найти «k самых близких» к запросу. У нас — **ChromaDB** в режиме `PersistentClient` (просто папка на диске). | Part 1, 2 |
| **Чанк (chunk)** | Кусок файла, который индексируется как одна запись. Требование: **чанк = одна функция / класс / блок конфига**, а не «каждые 50 строк». | Part 1 |
| **Retrieval / top-k** | Поиск k самых похожих чанков на запрос. | Part 2 |
| **Similarity score** | Число «насколько похоже» (обычно `1 - distance`). Показывается в UI. | Part 2 |
| **RAG** (Retrieval-Augmented Generation) | Схема: нашли релевантные чанки → вставили их в промпт → модель отвечает, опираясь на них. | Part 2 |
| **BM25** | Классический поиск по ключевым словам (как в старых поисковиках). Хорошо ловит точные имена функций, которые эмбеддинги могут пропустить. Библиотека `rank_bm25`. Используется как **ре-ранкер** поверх Chroma. | Part 2 |
| **Галлюцинация** | Модель уверенно выдумывает несуществующее (например, функцию, которой нет). Главный враг в `/ask`. | Part 2 |
| **Промпт** | Текст-инструкция, который ты отправляешь модели. | Part 2, 3 |
| **JSON-mode** | Ollama умеет заставить модель отвечать строго валидным JSON (`"format": "json"`). | Part 3 |

Больше ничего из ML знать **не обязательно**: ни нейросети, ни обучение, ни GPU.

## 2. Разбор задания по главам (близко к тексту)

### Глава I — Preamble (схема)
Четыре конвейера:

1. **INDEX**: кодовая база → чанкер (логические блоки, AST/regex) → эмбеддер (`all-MiniLM-L6-v2`, локально) → векторная БД (ChromaDB, persistent) → **watcher** (инкрементально, по хэшу содержимого).
2. **ASK**: вопрос («где используется X?») → retriever (top-k чанков + **BM25 rerank**) → instruct LLM (`qwen2.5:3b` через Ollama) → **обоснованный ответ** (сниппеты + факты, без галлюцинаций).
3. **PATCH**: намерение («добавь роут /healthz») → retriever (top-k чанков + **symbol facts**) → coder LLM (`qwen2.5-coder:3b`) → **JSON-патч** `{summary, files:[{path, op, content}]}`.
4. **APPLY & VALIDATE**: sanity-проверки (запрет заглушек, усыхания файла, >3 файлов) → **атомарная запись** (`*.ioc.tmp`, потом `os.replace`) → валидация (`py_compile` или команда из конфига) → **тихий реиндекс** изменённых файлов.
   При провале валидации — повтор до 3 раз с логом ошибки, затем **rollback** (снапшот восстанавливается байт-в-байт).

### Глава II — Foreword
Мотивация: «не плати $20/мес вендору — собери своё за выходные». Четыре части общаются друг с другом; жёсткое правило: **если патч ломает проект — система откатывается, как будто ничего не было**.

### Глава III — Introduction
- Три идеи: RAG по коду, оркестрация локальной LLM, автоматическая правка кода под валидацией.
- **Всё локально. Удалённая LLM = 0 баллов.**
- Части связаны: индекс Part 1 питает поиск Part 2, API Part 2 несёт патч-цикл Part 3.
- «Прочитай весь документ, прежде чем писать код».

### Глава IV — General guidelines
- Всё в **изолированном окружении** (VM или контейнер; Docker — простой путь).
- Файлы — в корне репозитория в папках **`p1`, `p2`, `p3`** и опционально `bonus`.
- Язык любой (примеры на Python — его и берём).
- LLM — **локально через Ollama** (или аналог).
- Векторная БД — локально, эталон — **ChromaDB `PersistentClient`**.
- Модель ≤3B. Рекомендация: `qwen2.5:3b` для `/ask` + `qwen2.5-coder:3b` для патчей (одной модели хватает для сдачи, две — лучше).

### Глава V — Demo application
- В репозитории должно лежать **своё маленькое демо-приложение** — это и есть «target project», на котором всё показывается проверяющему.
- Маленькое: 3–4 файла, один класс с 4–5 методами, точка входа. На скриншотах это приложение заметок: `main.py`, `notes/{__init__,cli,service,storage}.py`, `tests/test_service.py`, `README.md`, `ioc.config.yml`.
- **Нельзя** натравливать на большие проекты (ядро Linux и т.п.) — 3B-модель не справится.
- Команда валидации задаётся в **`ioc.config.yml`** в корне target-проекта (compile check, тесты, линтер или цепочка).

### Глава VI.1 — Part 1: индексация и синхронизация
Нужно:
- Скрипт вида `p1/index.py <target_path>` → обходит папку, режет файлы на **логические** чанки, считает эмбеддинги, сохраняет в коллекцию ChromaDB.
- **Watch-режим**: реагирует на события файловой системы и поддерживает коллекцию в актуальном виде.

Жёсткие ограничения:
- Чанкинг по структуре кода (функция / класс / блок конфига). **Fixed-size чанкер не проходит.**
- Эмбеддинги локально (`all-MiniLM-L6-v2`), модель скачивается один раз, дальше — **полностью офлайн**.
- **Инкрементальный реиндекс**: изменили один файл — трогаются только его чанки; удалили файл — его чанки удаляются из БД. **Полный реиндекс на каждое изменение не проходит.**
- Пропускать `node_modules`, `.git`, `dist`, `build`, `venv`, `.venv`, `__pycache__`, скрытые папки, бинарные файлы. **Папку самой ChromaDB никогда не индексировать** (иначе watcher реагирует на собственные записи).

Дашборд, вкладка **Overview**: число чанков, путь к target, путь Chroma, модели (эмбеддинг/LLM), бэкенд Ollama, число чанков по файлам, **live-лента событий** watcher’а. Вкладка **Files** (на скриншоте): содержимое файла с отметками границ чанков — границы должны совпадать с определениями методов.

Подсказки из текста:
- Хэшируй каждый чанк, чтобы понимать, что реально изменилось.
- В Docker bind-mount (btrfs/overlay) inotify **теряет события** → нужен **polling-fallback**.
- Модуль Python `ast` даёт точные диапазоны строк функций/классов (с декораторами и вложенными методами); regex — запасной вариант для не-Python файлов и файлов, которые не парсятся.

### Глава VI.2 — Part 2: Architect API и RAG
- HTTP-сервер (**FastAPI**) поверх коллекции: **retrieval** (вернуть top-k чанков) и **RAG** (чанки → LLM → обоснованный ответ).
- Сервер живёт рядом с watcher’ом и использует **один Chroma-клиент на процесс**.
- Рекомендованный набор эндпоинтов:
  - `GET /status`, `GET /files`, `GET /file?path=...`, `GET /chunks` (с пагинацией);
  - `POST /context` — top-k чанков со score;
  - `POST /ask` — retrieve-then-generate;
  - `GET /events` — поток событий файлов через **SSE** (Server-Sent Events).
- Вкладка дашборда **Ask & Retrieve**: поле вопроса, выбор `k`, кнопки «Retrieve» и «Ask LLM», ответ + список источников со score. (На скриншоте ещё вкладка **ChromaDB Explorer** — просмотр сырых чанков.)
- **Ключевое требование оценки**: на вопросах «есть ли функция X?» и «какие функции в этом файле?» `/ask` **не должен выдумывать** символы, которых нет в индексе. Оценивается **правдивость**, а не красноречие.
- Подсказка: **не лечить это промптом**. Индекс и так точно знает, какие символы есть → **ответить на такие вопросы детерминированно из метаданных** (или подложить «факты о символах» до того, как модель заговорит).
- Подсказка: эмбеддинги слабы на точных идентификаторах → **BM25-ре-ранкинг** в памяти (`rank_bm25`). Chroma остаётся основным хранилищем.

### Глава VI.3 — Part 3: генерация, применение, цикл валидации
Пользователь пишет намерение → система: генерирует патч → проверяет → применяет → валидирует → **либо фиксирует, либо откатывает к точному исходному состоянию**.

- Сдаётся **цикл**, а не набор эндпоинтов. HTTP-раскладка — на твой выбор, но проверяющий должен прогнать полную итерацию из вкладки **Patch Loop**.
- Формат патча — **структурированный JSON, не diff и не свободный текст**:
  ```json
  {"summary": "...", "files": [{"path": "main.py", "op": "create|modify|delete", "content": "<ПОЛНЫЙ новый текст файла>"}]}
  ```
- Валидация — команда из `ioc.config.yml`; базовая: `python -m py_compile {files}`.
- **Sanity-проверки (жёсткий отказ до записи на диск)** — отклонить патч, если он:
  1. содержит в `content` служебные маркеры ретривала (например, `### chunk ...`, `[source: ...]`);
  2. делает `create` для уже существующего файла;
  3. заменяет непустой файл на `""`, `"None"` или `"null"`;
  4. определяет функцию, тело которой — только заглушка (`pass`, `...`, `return None`);
  5. уменьшает существующий файл **больше чем на 60%**;
  6. трогает **больше 3 файлов**.
- Дальше: атомарная запись → запуск валидации → при ошибке лог отдаётся модели на новую попытку → после **3 неудачных итераций — rollback**.
- **Rollback должен вернуть проект в точное исходное состояние** (частичный откат не проходит). Снапшот каждого затрагиваемого файла — до записи.
- Подсказка: пишем каждое изменение во временный `*.ioc.tmp`, и только когда **все** временные файлы готовы — `os.replace` на место (атомарно в пределах одного тома).

### Глава VII — Bonus (только если обязательная часть **идеальна**)
- `POST /reindex` — полный реиндекс по запросу;
- авто-`git commit` валидного патча с сообщением от LLM;
- Docker SDK: следить за логами сервиса и запускать патч-цикл при падении;
- dry-run: показать diff без записи на диск;
- богатый дашборд: визуальный diff, live-статус валидации через SSE.

### Глава VIII — Сдача
- В корне: `p1`, `p2`, `p3` (+ `bonus`).
- **`README.md`** — как запустить; **`Makefile`** — `make up` / `make down` (например, через `docker compose`). Проверяющий должен запустить проект, **не читая исходники**.
- **Никогда не коммитить** веса LLM, архив эмбеддинг-модели, заполненную папку ChromaDB → всё в `.gitignore`. Иначе — отказ сразу.

## 3. Целевая архитектура

```
docker compose
├── ollama              (образ ollama/ollama, порт 11434, том с моделями)
└── ioc                 (Python: indexer + watcher + FastAPI + статический дашборд)
       ├── монтирует ./demo  → /workspace          (target project)
       ├── Chroma-папка вне target или в исключённой /workspace/.chroma
       └── кэш эмбеддинг-модели в volume (не в git)
```

Предлагаемая структура репозитория:

```
.
├── Makefile               # up, down, logs, pull-models, index, clean
├── README.md
├── docker-compose.yml
├── .gitignore             # .chroma/, models/, *.ioc.tmp, __pycache__, .venv ...
├── demo/                  # target project (приложение заметок)
│   ├── ioc.config.yml     # validate: "python -m py_compile {files} && python -m pytest -q"
│   ├── main.py
│   ├── notes/{__init__,cli,service,storage}.py
│   └── tests/test_service.py
├── p1/                    # индексатор
│   ├── index.py           # CLI: python index.py <target> [--watch]
│   ├── chunker.py         # AST + regex fallback + YAML/MD блоки
│   ├── embedder.py        # sentence-transformers all-MiniLM-L6-v2
│   ├── store.py           # обёртка над ChromaDB
│   ├── watcher.py         # watchdog + PollingObserver fallback
│   └── dashboard/         # Overview + Files
├── p2/                    # API + RAG
│   ├── server.py          # FastAPI: /status /files /file /chunks /context /ask /events
│   ├── retriever.py       # Chroma top-k + BM25 rerank
│   ├── symbols.py         # детерминированные ответы про символы
│   ├── llm.py             # клиент Ollama
│   └── dashboard/         # + Ask & Retrieve, ChromaDB Explorer
└── p3/                    # патч-цикл
    ├── patcher.py         # генерация JSON-патча
    ├── sanity.py          # 6 проверок
```

## 4. План работ по шагам

### Этап 0. Окружение (0.5–1 день)
- [ ] Установить Docker + Docker Compose. Проверить, что хватает RAM (желательно **8+ ГБ**; каждая модель ~2 ГБ; работает и на CPU, просто медленнее).
- [ ] `docker run ollama/ollama`, затем `ollama pull qwen2.5:3b` и `ollama pull qwen2.5-coder:3b`.
- [ ] Проверить руками: `curl localhost:11434/api/generate -d '{"model":"qwen2.5:3b","prompt":"hi","stream":false}'`.
- [ ] Python 3.11+, venv. Поставить: `chromadb`, `sentence-transformers`, `watchdog`, `fastapi`, `uvicorn`, `rank_bm25`, `pyyaml`, `httpx`.
- [ ] `.gitignore` сразу (модели, `.chroma/`, кэш HF, `*.ioc.tmp`).

### Этап 1. Демо-приложение (0.5 дня)
- [ ] `demo/`: приложение заметок — `Storage` (in-memory), `NoteService` (create/find/search/by_tag/remove), `cli.py`, `main.py`, тесты на pytest.
- [ ] `demo/ioc.config.yml` с командой валидации.
- [ ] Убедиться, что `python main.py` и тесты работают.

### Этап 2. Part 1 — индексатор (2–4 дня)
- [ ] **Обход файлов** с исключениями (список папок, скрытые, бинарные — проверка на `\0` в первых байтах, папка Chroma).
- [ ] **Чанкер**:
  - `.py` → `ast.parse`, обойти дерево: модульный «шапочный» блок (импорты, docstring), каждый класс (заголовок класса), каждый метод/функцию (включая async и декораторы — `node.decorator_list[0].lineno`), с `lineno`/`end_lineno`.
  - если `ast` упал (синтаксическая ошибка) → regex по `^\s*(def|class|async def)`.
  - `.yml/.yaml` → по ключам верхнего уровня; `.md` → по заголовкам; остальное → regex/целиком если маленький.
  - Метаданные каждого чанка: `path`, `start_line`, `end_line`, `kind` (function/class/method/config), `symbol` (имя, например `NoteService.search`), `hash` (sha256 текста).
  - ID чанка детерминированный: например `path::symbol::start_line` или `path::sha`.
- [ ] **Эмбеддер**: `SentenceTransformer("all-MiniLM-L6-v2")` — скачать один раз в кэш-том; потом выставить `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` и проверить, что всё работает **без сети**.
- [ ] **Хранилище**: `chromadb.PersistentClient(path=...)`, одна коллекция, `upsert`/`delete(where={"path": ...})`.
- [ ] **Инкрементальность**: хранить хэш файла; при изменении — перечанковать только этот файл, удалить из Chroma чанки, которых больше нет, добавить новые/изменённые (по хэшу). При удалении файла — `delete(where={"path": p})`. При переименовании — delete + add.
- [ ] **Watcher**: `watchdog.Observer`; флаг/автодетект для `PollingObserver` (на Docker bind-mount); debounce ~300 мс (редакторы пишут файл несколькими событиями); фильтр исключённых путей.
- [ ] **Лента событий**: в памяти очередь последних N событий (`modified notes/service.py: +1 −1 chunks`) — пригодится для SSE.
- [ ] **Дашборд Overview + Files**: простой HTML+JS (без фреймворков) или Streamlit. Для Files — показать файл с маркерами ▶ на `start_line` каждого чанка.
- [ ] **Проверки руками**: изменить метод → поменялся только 1 чанк; удалить файл → чанки ушли; создать файл → появились; watcher не реагирует на `.chroma`.

### Этап 3. Part 2 — API и RAG (2–4 дня)
- [ ] FastAPI-приложение, при старте: один Chroma-клиент, загрузка эмбеддера, запуск watcher’а в фоне (поток).
- [ ] `GET /status` (кол-во чанков, пути, модели, URL Ollama), `GET /files`, `GET /file?path=` (с защитой от `../` — path traversal!), `GET /chunks?offset=&limit=`.

## 5. Что нужно знать / подтянуть

**Обязательно (не-ML навыки):**
- Python: модули, классы, `pathlib`, `subprocess`, `hashlib`, `os.replace`, потоки (`threading`) или `asyncio`.
- Модуль **`ast`** (обход дерева, `lineno`/`end_lineno`).
- **HTTP/REST**, JSON, **FastAPI** (роуты, pydantic-модели), **SSE**.
- Немного **HTML/JS** (fetch, EventSource) для дашборда.
- **Docker / docker compose / Makefile**, тома (volumes), bind-mount.
- Файловые события: библиотека **watchdog**, понимание inotify и почему нужен polling.
- Git, `.gitignore`.

**Из «ML-мира» — только практическое использование:**
- Ollama API: `/api/generate` и `/api/chat`, параметры `format: "json"`, `options.temperature`, `num_ctx`.
- `sentence-transformers`: `model.encode(texts)` → векторы. Всё.
- ChromaDB: `PersistentClient`, `get_or_create_collection`, `add/upsert/query/get/delete`, фильтр `where`.
- `rank_bm25`: `BM25Okapi(tokenized_docs).get_scores(query_tokens)`.
- Базовый **prompt engineering**: системная инструкция, few-shot примеры, «отвечай только по контексту», строгий формат вывода.
- Понимание ограничений маленьких моделей: малое окно контекста, склонность выдумывать, нестабильный JSON → поэтому валидация, повторы и детерминированные ответы там, где возможно.

**Куда смотреть:** документация Ollama (API), ChromaDB «Getting started», sentence-transformers «Quickstart», FastAPI tutorial, `docs.python.org/3/library/ast.html`, watchdog docs.

## 6. Подводные камни и что проверят на защите

- Чанки должны совпадать с границами функций (проверят во вкладке Files).
- Изменение одного файла не должно переиндексировать всё; удаление — чистить БД.
- Watcher не должен зацикливаться на собственной папке Chroma и на `*.ioc.tmp`.
- В Docker события inotify могут не приходить → polling.
- `/ask` не должен выдумывать функции — будут специально спрашивать про несуществующие.
- Патч только JSON с полным содержимым файла; все 6 sanity-правил — **жёсткие** отказы.
- После неудачного цикла — **ни одного изменённого байта** (проверят через `git status`/`diff`).
- Проверяющий будет «ломать» систему странными запросами: пустые строки, огромный `k`, `path=../../etc/passwd`, просьба удалить все файлы, переименование в 5 файлах и т.п. — система должна вежливо отказывать, а не падать.
- Никаких облачных API, никаких весов в git.
- Ответы маленькой модели медленные (секунды–десятки секунд на CPU) — ставить разумные таймауты и показывать прогресс в UI.
